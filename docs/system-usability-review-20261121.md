## 本次實作

1. 電視天氣：將六地現有天氣文字合併成同一段，以「｜」串接，在原跑馬燈完整跑過；之後接公告／台股，不新增天氣列、不增加查詢。來源三十分鐘天氣快取及五分鐘航班快取不變。
2. 點數發放：取代長下拉選單，使用姓名搜尋、每頁二十位、目前點數、固定已選姓名摘要。已載入的電話也可搜尋；首頁直接進入點數時帳戶回應只有姓名與車商 ID，不保證有電話，因此不額外下載完整司機資料。搜尋只重繪名單，不清除點數與原因。確認框列出對象、發放／扣回數量與原因，確認階段也防連點。原交易帳本、request_id 防重、權限與扣點限制不變。
3. 費用管理：新增姓名／已載入手機／內容搜尋，車商、類型、狀態、日期區間篩選；待確認優先、日期排序、每頁五十筆，頁首及頁尾都可換頁。金額與日期保持清楚，狀態統計跟隨篩選。使用「待確認金額」而非「未收金額」，因 paid 在目前介面代表已確認，並無實際銀行對帳憑證。薪資日期不當成繳款逾期；非薪資逾期待確認才警示。
4. 司機薪資通知尚未驗證時，卡片摘要不再直接顯示金額。這只是 UI 修正，並不代表後端已新增二次驗證或資料加密。

## 需要先排程的項目

### 優先一：敏感資料與資料正確性

- 薪資二次驗證目前在 app.js 的 unlockSalary 分支比對 state.user.national_id，payment_notices 由 data-api 的 loadDriverData 依 driver_id 查詢後傳回整筆。其範圍是本人已登入工作階段，未發現此路徑讓其他司機讀取，但前端遮罩不能提供真正的二次授權。建議伺服器另做短效驗證／解鎖 API，在驗證前不回傳金額、正文與附件，且簽署附件時也檢查本人與解鎖狀態。需要連同既有舊附件路徑與身分資料政策測試，不能只改卡片或寫成「已加密」。
- 金錢與保險重要變更應逐一確認有操作者、版本衝突及狀態異動紀錄；既有點數交易與保養／車檢專用流程可沿用，不能改回一般整筆 upsert。
- 費用後續應明確分「應收、發放、代扣」；目前類型含薪資與欠費，不能直接把全部金額加成公司應收。是否要已付款／付款日期／收據／對帳狀態，須先確認業務定義，再新增欄位與增量 migration。

### 優先二：降低傳輸及首屏等待

- app.js 本次約 758 KB 原始碼、styles.css 約 251 KB（未壓縮大小，非網路實測值）。建議分成車輛、保險、財務、人員等功能模組，進頁才載入，保留現有登入、路由、權限與草稿。不需要換框架或重建產品。
- data-api loadAdminData 仍將工作區選定資料表以 Promise.all 查詢，多處 select('*')。首頁縮小載入已有效，但第一次進一般工作區仍可能拉多個模組。應逐功能新增帶白名單欄位的查詢、伺服器排序／游標／篩選與摘要 RPC，保留明確總筆數與舊記錄入口。**本次費用五十筆為前端顯示分頁，不會減少既有 load 的資料庫傳輸量。**
- 所有輪詢統一加上離頁停止、hidden 暫停、同請求合併與失敗退避。現有聊天已增量、派趟已按日、電視 R2 共用快取，不應為統一而退回整包下載。
- 觀測要區分查詢次數、回應 bytes、照片原圖 bytes、R2 與 Supabase Egress；前端更快不等於 Supabase 更省。發布前後以相同人數／使用路徑量測，再決定是否需遷移主機。

## 驗證與限制

- 針對這次變更測試：一千位合成帳戶搜尋／二十位分頁、選取後草稿保留、一次確認只送一筆、費用一百二十筆五十筆分頁、篩選／重設、HTML 跳脫、320／390／768／1440px 無橫向溢出。
- 延續點數交易、兌換與用品防重測試，及看板取消／八小時／原輪播回歸；新測試不寫正式帳本。
- 本次是前端操作改善，未新增或刪除任何資料庫表／資料、未變更收款規則、未把所有建議一次部署。完整建議應分階段，逐批備份、測試與發布。
